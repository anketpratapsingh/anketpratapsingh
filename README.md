### 📡 Mobilytix Realtime Marketing (MRTM)
> Real-time offer decisioning platform for telecom operators

Comviva's flagship real-time marketing platform, live with multiple telecom operators internationally (AT&T, Optus, Vodafone, IOH and more). MRTM watches subscriber behaviour as it happens — recharges, usage, purchases, app events — and reacts **within seconds** with the right personalised offer on the right channel. The hard part isn't any single feature: it's sustaining millions of events per day through a multi-stage decisioning pipeline at sub-second latency and 99.9% uptime.

**How the pipeline works:**
1. **Event ingestion** — operator systems and external sources (apps, webhooks, Kafka connectors) push subscriber events; the event processor normalises source payloads into MRTM events and publishes them to Kafka topics
2. **Trigger evaluation (ERED)** — the event rule engine evaluates every event against active campaign triggers and rules to decide which subscribers qualify, in real time
3. **Journey execution (ECMP)** — qualified subscribers move through multi-step campaign journeys (communication, wait, condition, API steps) with stateful step-by-step orchestration
4. **Delivery & feedback** — offers and messages go out through SMS, USSD, email, push and other channels, with provider responses fed back into the journey
5. **Reporting & LiveMetrics** — campaign performance, subscriber counts, and delivery metrics via ETL pipelines and real-time dashboards

**My role across 4 years and 5 major versions (v5.6 → v7.11.1 → v7.12.2 → v8.1.2 → v8.3.0):** grew from feature development to **owning 100% of the SDLC** — requirements, LLD, development, SIT/UAT, production deployment, and post-release support across multiple live operator environments. Led version upgrades and migrations for live operators — moving production deployments across major platform versions without service disruption.

**What I worked on across the platform:**
- ⚡ **Trigger & campaign execution** — ERED rule evaluation, campaign qualification, and offer allocation logic
- 🧭 **Journey orchestration** — ECMP step transitions (communication, wait, condition steps) and move-customer processing that steps subscribers through multi-stage journeys
- 🔌 **Event pipeline** — event processor development: consuming source events, transforming payloads into MRTM events, and routing across Kafka topics
- 📨 **Multi-channel notifications** — delivery integrations with provider request/response handling and communication history
- 📊 **Reporting & LiveMetrics** — campaign metrics, ETL-generated campaign bases, and count-reconciliation logic
- 🚀 **In-memory decisioning** — Hazelcast plus an in-memory database keeping hot subscriber/campaign state in memory to hold sub-second decisioning latency at millions of events per day: **VoltDB up to v7.11.1, SingleStore from v7.12.2 onward** — so I've built and operated the decisioning layer on both, through the platform's migration

### 📲 Just For You (J4U)
> USSD-based real-time offer interface

The subscriber-facing front door to MRTM's personalised offers: a customer dials a USSD short code and browses an interactive menu of offers picked for them **at that moment** — no smartphone, no app, no data connection required. USSD is what makes personalised marketing reach *every* subscriber, including feature-phone users in emerging markets — and it's also what makes the engineering hard.

**Why it's technically demanding:**
- ⏱️ **Hard latency budget** — USSD gateways time out fast; every menu screen must render in **under 200ms end-to-end**, including a live gRPC call to MRTM for real-time offers
- 🔄 **Stateless protocol, stateful conversation** — USSD gives you one request/response at a time, but a subscriber navigates a multi-screen menu (browse → select → confirm). Session state lives in **Hazelcast**, so any node in the cluster can serve the next screen of an in-flight conversation
- 🌍 **Multilingual rendering** — menu templates rendered per subscriber language at request time
- 💳 **Multiple wallet payment support** — subscribers pay for selected offers through their choice of mobile-money wallet, with wallet selection and payment confirmation handled inside the same USSD session
- ◀️ **Back option on every menu** — backward navigation in a protocol that has no concept of "back": the session keeps a menu-history stack in Hazelcast, so subscribers can step back through screens without restarting the flow
- 🔁 **Closed-loop offer fulfilment** — on confirmation, J4U triggers offer allocation in MRTM and the acceptance event feeds back into the subscriber's campaign journey, so every conversion updates journey state in real time
- 📈 **High concurrency** — thousands of subscribers in simultaneous menu sessions during campaign pushes

**Request flow:**
```
Subscriber dials → USSD Gateway → Spring Boot service → gRPC to MRTM (live offers)
→ Hazelcast (session state + menu-history stack) → menu rendered <200ms
→ offer selected → wallet payment → Kafka (async event logging)
```

**Impact:**
- ⬆️ 25% improvement in API response time after systematic profiling and targeted optimisation
- ✅ Real-time offer retrieval via gRPC + Kafka — sub-200ms end-to-end sustained under load
- ✅ Distributed session management via Hazelcast — no sticky sessions, full horizontal scalability

**Stack:** `gRPC` `Kafka` `Spring Boot` `Hazelcast` `USSD` `JPA/Hibernate`

### 🔀 Integration Gateway (CUIG)
> Centralised upstream/downstream integration hub

A centralised integration gateway that sits between the telecom product suite and every external system it talks to — upstream sources sending events in, and downstream systems (fulfilment platforms, notification providers, operator systems) receiving calls out. Before CUIG, **every new integration meant custom code, a build, and a deployment**; CUIG replaced that with a single gateway where a new integration is a configuration entry.

**The design problem it solves:** external systems all speak different formats and protocols (XML/JSON, sync/async, different auth). CUIG normalises all of that behind one hub — so product services integrate once with CUIG, and CUIG handles the per-partner differences via configuration.

**How it works:**
- 🔀 **Dual-protocol in one gateway** — synchronous HTTP (request/response) and asynchronous Kafka (fire-and-forget / event-driven) flows, chosen per integration via config
- 🔧 **XSLT transformation engine** — per-integration message mapping (XML ↔ JSON, field renames, structure reshaping) defined as XSLT config, not code
- 📋 **Config-driven onboarding** — endpoints, transformations, routing, headers/auth, and retry behaviour defined through the GUI + Config Service; picked up dynamically with zero code deployment
- 🧭 **Consul-backed service discovery & dynamic configuration** across all gateway microservices
- 🔁 **Resilience built in** — retries, error handling, and failure visibility for every integration flow

**Modules (independently deployable microservices):**
| Module | Responsibility |
|---|---|
| GUI + Config Service | Define and manage integrations — endpoints, mappings, routing rules |
| Gateway Service | Synchronous HTTP entry/exit point for request-response integrations |
| Event Processor | Asynchronous Kafka-based flows — consuming and publishing integration events |
| Interactive Service | Request/response flows requiring session-style interaction |
| Fulfilment Service | Outbound calls to downstream fulfilment/provisioning systems |
| User Service | Authentication and access control for the gateway |

**Impact:**
- ⬇️ **90% reduction in deployment effort** — new integrations onboarded via config entry instead of code + build + release cycle
- ⏱️ Integration turnaround dropped from a **development sprint to a configuration task**
- ✅ One consistent integration surface for the whole product suite — every new partner system stopped being a bespoke project

**Stack:** `Spring Boot` `Apache Kafka` `Consul` `PostgreSQL` `XSLT` `REST APIs` `Microservices`

### 🎟️ Coupon Management System (CMS)
> End-to-end coupon lifecycle platform — owned from HLD/LLD to production

A coupon lifecycle platform for telecom marketing campaigns, covering the full journey of a coupon: **campaign setup → bulk coupon generation → allocation → reservation → redemption → expiry**. Coupons are awarded to subscribers through marketing campaigns and redeemed across channels — making correctness under concurrency (no double-redemption, no over-allocation) the core design problem. **Owned end-to-end: High-Level Design → Low-Level Design → development → SIT/UAT → production.**

**Design (HLD/LLD authored by me):**
- 📐 Complete **HLD & LLD** — component architecture, sequence flows for every lifecycle transition, ER model, interface contracts, and capacity estimates
- 🔄 **State-machine-driven lifecycle** — every coupon moves through controlled states (generated → allocated → reserved → redeemed / expired / cancelled), so no invalid transition is possible
- 🔒 **Idempotent, concurrency-safe redemption** — duplicate redemption requests and race conditions handled at design level, preventing double-redemption at scale
- ⚙️ **Config-driven validation rules** — per-subscriber limits, validity windows, channel eligibility, and new coupon types onboarded via configuration, without code changes

**Build & operate:**
- ✅ REST APIs for campaign systems and redemption channels; event-driven processing via Kafka
- ✅ Full **audit trail** of every coupon state change for reconciliation and dispute handling
- ✅ Scheduled **expiry processing** and reporting for campaign owners
- ✅ Delivered through SIT/UAT into production with post-release monitoring

**Stack:** `Java` `Spring Boot` `Apache Kafka` `PostgreSQL` `REST APIs` `Microservices` `State Machine` `HLD/LLD`

### 🕸️ Travsr *(Open Source Contributor)*
> The code graph that lives next to git · [travsr.com](https://travsr.com/)
>
> Repos: [travsr](https://github.com/Travsr-com/travsr) (core engine, CLI, daemon, MCP, VS Code) · [travsr-embed](https://github.com/Travsr-com/travsr-embed) (embedding sidecar) · [travsr-lang](https://github.com/Travsr-com/travsr-lang) (language plugins)

**The problem.** AI coding agents usually understand a codebase by splitting it into text chunks and searching for the ones that look similar to the question. That is why they name files that merely *look* related instead of the code that actually calls a function, miss callers that live three modules away, and burn thousands of tokens reading files they did not need.

**What Travsr does.** Travsr treats source code as what it really is: a graph. It indexes a repository into real call, import, and reference edges, using Tree-sitter for fast structural parsing and sandboxed SCIP/LSIF analyzers for deep, compiler-accurate semantics. A git hook and a file watcher keep the graph fresh on every save and commit. The graph is served over the **Model Context Protocol (MCP)**, so Claude Code, Cursor, GitHub Copilot, Codex, and Gemini CLI can answer *"who calls PaymentService.charge?"* by following real edges, with far fewer tokens and no invented dependencies. It is open source (Apache-2.0), runs entirely on the developer's machine, exposes 26 MCP tools, and supports 14 language groups.

**My role.** I contribute across all three repositories (core engine, embedding sidecar, language plugins) and the VS Code extension, mainly in Rust and TypeScript. I take on the hard, unglamorous problems that decide whether a local-first developer tool can be trusted: Windows-only bugs, unbounded memory, sandbox security gaps, and graph answers that look right but are quietly wrong.

### 🧪 AutoTest Agent — Java Unit-Test Generation

- 🔀 **By diff** — `/autotest --diff` → tests only for what changed in the working tree, ideal before raising an MR
- 📋 **From acceptance criteria** — paste a story's AC and it derives the test scenarios directly from the requirements

- ✅ Covers happy paths, edge cases, boundary values, and exception flows automatically
- ✅ Mocks external dependencies (Kafka producers, repositories, gRPC clients) correctly out of the box

**How it helps:** Writing a thorough test suite for a service class used to take an engineer **hours per class** — the agent produces a compiling, passing suite in **minutes**, and applies the same conventions every time. ### 🔍 Code Review Agent — AI Reviews in GitLab
> Automated merge-request review integrated into the GitLab workflow

**How it works:** when an MR is raised, the agent reviews the **diff in context** — not just the changed lines, but how they interact with the surrounding code — and posts its findings **directly on the MR as inline comments**, anchored to the exact lines, so developers fix issues in place like any other review thread.

**What it checks:**

- 🧪 **Test coverage** — changed behaviour without corresponding test changes gets flagged

- ✅ Findings are **severity-ranked** so reviewers see the critical issues first, not a wall of nitpicks
- ✅ Same standard on every MR — the review bar no longer depends on which reviewer was available

**How it helps:** Developers get first-pass review feedback in **minutes instead of waiting hours or days** for a human reviewer to free up — so obvious bugs, standards violations, and nit-level issues are fixed before anyone else looks at the MR. Human reviewers now spend their time on design and architecture decisions rather than style policing, and MRs reach merge-ready state in fewer review cycles.
